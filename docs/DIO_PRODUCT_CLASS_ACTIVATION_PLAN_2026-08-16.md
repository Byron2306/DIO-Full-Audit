# DIO Product Class Activation Plan

Corrected after full integration review: `2026-08-16`

## Core Move

Do not build 38 new engines, and do not pretend 38 wrappers are already products.

The correct activation path is:

`registered class → typed route → controlled execution → reviewed artifact → public-safe proof → operator launch`

The 38 profile extensions remain compositions over the DIO organism. Their likely processors are already visible, but a likely processor is not an executable route contract.

## Required Graduation Contract

Every class must pass the same gates:

1. **Typed profile**: inputs, outputs, authority, claim ceiling, processor adapter.
2. **Source authority**: explicit permissions required by that class.
3. **Controlled fixture**: buyer-shaped, non-sensitive source material.
4. **Execution receipt**: the actual processor route ran successfully.
5. **Human review**: output and domain-specific authority recorded.
6. **Public-safe proof**: redacted artifact that can be served from the tracked public site.
7. **Launch approval**: operator decides whether to expose intake/campaign surfaces.
8. **Commercial learning**: conversion, manual time, revisions, revenue and repeat intent.

## Anti-Sprawl Rule

`DIO PRODUCT CLASS = existing work pattern × META composition × typed profiles × existing organs`

A class becomes a new infrastructure organ only if the required capability genuinely does not exist anywhere in the organism. Otherwise the work is route/profile/proof construction, not repo or engine proliferation.
